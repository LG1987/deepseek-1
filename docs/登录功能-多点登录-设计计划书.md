## 1. 项目背景与目标

### 1.1 背景

现有系统使用「单 Token 无状态鉴权」：登录后签发一枚长效 JWT，服务端不记录任何会话信息。该方案在业务扩张后暴露三类问题：

1. **无法主动下线**。用户改密码、手机丢失、员工离职时，已签发的 Token 在过期前始终有效。
2. **无法多端管理**。用户看不到自己有哪些设备在线，也无法「只登出某一台设备」。
3. **无法审计**。没有登录记录、设备记录与异常登录识别能力。

### 1.2 目标

建设一个独立的认证服务 `auth-service`，提供：

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 账号密码注册与登录 | 登录成功率 ≥ 99.9%，P99 响应 ≤ 200ms |
| G2 | 多设备并行在线 | 手机、平板、PC、小程序可同时在线，互不干扰 |
| G3 | 会话可视化与精细下线 | 用户可列出全部在线设备，可单独登出任意一端 |
| G4 | 凭证可主动失效 | 撤销会话后，Access Token 在 ≤ 30s 内失效 |
| G5 | 凭证安全 | 满足 OWASP ASVS L2 相关条目，通过渗透测试 |
| G6 | 工程可交付 | 有 CI/CD、测试覆盖、可一键本地启动、代码入库规范 |

### 1.3 非目标（本期明确不做）

- 不做 OAuth2 授权服务器（暂不对外颁发第三方 access token）。
- 不做 SSO 联邦登录（CAS/SAML）与企业 LDAP 对接。
- 不做完整 RBAC 权限体系，只提供 `sub`、`roles`、`scopes` 声明，细粒度鉴权由各业务服务自行实现。
- 不做短信/邮件通道自身的建设，只对接现有供应商 SDK。
- 不做风控画像与设备指纹高级算法，一期仅记录设备基础信息。

### 2.2 非功能性需求

| 类别 | 指标 |
| --- | --- |
| 性能 | 登录 P99 ≤ 200ms；令牌校验 P99 ≤ 20ms（Redis 命中） |
| 并发 | 单实例 ≥ 2000 QPS 校验；峰值支撑 1000 次/秒登录 |
| 可用性 | 99.95%；认证服务不可用时业务侧降级策略明确 |
| 一致性 | 会话状态最终一致；撤销操作强一致（先落库后清缓存） |
| 安全 | 传输 TLS1.2+；密码不可逆哈希；令牌不落明文日志 |
| 可观测 | 结构化日志 + Prometheus 指标 + 关键告警 |
| 兼容 | REST/JSON，接口版本化 `/api/v1`，向前兼容至少 2 个大版本 |
| 合规 | 支持数据导出与删除；IP/手机号按最小化原则存储 |

### 2.3 关键设计决策（ADR 摘要）

| 编号 | 决策 | 备选方案 | 选择理由 |
| --- | --- | --- | --- |
| ADR-01 | **双令牌**：短期 JWT Access Token + 服务端存储的不透明 Refresh Token | 纯 JWT 长效令牌 / 纯服务端 Session | 兼顾无状态校验的高性能与「可主动撤销」的安全诉求 |
| ADR-02 | 会话粒度 = **一次登录一台设备一条会话** | 一用户一条会话 | 多点登录语义要求各端独立撤销，必须按设备分会话 |
| ADR-03 | Refresh Token 使用**随机不透明串 + SHA-256 哈希存储** | JWT 形式的 Refresh Token | 不透明串可随时服务端吊销，且库中泄露也无法直接使用 |
| ADR-04 | 撤销 Access Token 采用 **Redis 黑名单（按 sid）** | 每次请求查库校验会话 / 缩短 Access Token 到 1 分钟 | 查库不可接受；黑名单 TTL = Access Token 剩余寿命，内存开销可控 |
| ADR-05 | Refresh Token **轮换 + 重放检测** | 不轮换 | 刷新令牌一旦被窃取，重放会被立即发现并整族撤销 |
| ADR-06 | 密码哈希使用 **Argon2id**（兼容期保留 BCrypt 校验） | 单纯 MD5/SHA | 抗 GPU 爆破；支持参数可调与渐进式升级 |
| ADR-07 | 认证服务**独立部署**，业务服务只做 JWT 本地校验 | 网关统一校验 | 减少网络跳数，业务服务仍可通过黑名单接口感知撤销 |

### 4.2 表结构 DDL（MySQL 8）

`t_user_session.revoked_reason` 取值枚举：`LOGOUT`（本端主动登出）、`LOGOUT_ALL`（登出全部设备）、`KICKED`（用户从设备列表踢出）、`ADMIN`（管理员封禁）、`REPLAY`（刷新令牌重放检测触发）、`PWD_CHANGED`（密码变更连带撤销）、`DEVICE_LIMIT`（超出在线设备上限被淘汰）。

### 4.3 JSON Web Token 载荷设计

Access Token（JWT，RS256 签名，有效期 30 分钟）：

```json
{
  "iss": "https://auth.example.com",
  "sub": "10086",
  "aud": "example-api",
  "sid": "01HZX8Q2K7VJ9M3NPR4T5W6YAB",
  "jti": "b7f3c1e0-9a2d-4f18-8c77-1d2e3f4a5b60",
  "typ": "access",
  "roles": ["USER"],
  "scopes": ["profile:read", "order:write"],
  "iat": 1760000000,
  "exp": 1760001800,
  "pwd_at": 1759000000
}
```

| 声明 | 用途 |
| --- | --- |
| `sub` | 用户 ID，业务服务直接用作主体标识 |
| `sid` | 会话 ID，撤销与多端管理的核心索引 |
| `jti` | 令牌唯一 ID，便于精确加入黑名单与追踪 |
| `typ` | 区分 access / refresh，防止令牌混用 |
| `pwd_at` | 密码最后修改时间；若密码在令牌签发后被修改则判定失效 |
| `roles`/`scopes` | 粗粒度授权信息，避免每次请求查库 |

Refresh Token：**不是 JWT**，而是 32 字节安全随机数的 Base64URL 编码（约 43 字符），数据库仅存 `SHA-256` 哈希。

### 4.4 Redis 键设计

| Key 模式 | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `auth:revoked:sid:{sid}` | String | Access Token 剩余寿命 | 会话撤销黑名单，校验时 O(1) 命中即拒 |
| `auth:revoked:user:{userId}:after` | String(时间戳) | Access Token 最大寿命 | 全局撤销（改密码/登出全部）后，签发时间早于此值的令牌一律失效 |
| `auth:login:fail:{account}` | String(计数) | 15 min | 失败次数计数，触发锁定与验证码 |
| `auth:lock:{account}` | String | 锁定剩余时间 | 快速判定锁定，避免查库 |
| `auth:captcha:{ticket}` | Hash | 5 min | 图形验证码答案 |
| `auth:ratelimit:login:{ip}` | String | 60 s | IP 维度登录限流 |
| `auth:sms:limit:{phone}` | String | 60 s | 短信发送频控 |
| `auth:user:sessions:{userId}` | Set | 与会话同寿命 | 在线设备列表快速读取（可选，DB 为准） |

> 一致性约定：所有撤销操作 **先写数据库，再写 Redis 黑名单**；写完 Redis 才返回成功。缓存写失败时通过领域事件重试，并有 30 秒兜底扫描任务比对 DB 与黑名单。

## 5. 核心流程时序

### 5.1 登录（多点登录：不冲击已有会话）

```
Client            API层           应用层            领域层          MySQL        Redis
  │  POST /login    │                │                 │              │            │
  │────────────────>│  参数校验+限流  │                 │              │            │
  │                 │───────────────>│  1.查用户         │              │            │
  │                 │                │────────────────────────────────>│            │
  │                 │                │  2.锁定/状态校验   │              │            │
  │                 │                │  3.校验密码(Argon2id)            │            │
  │                 │                │  4.失败→计数+1，写审计            │            │
  │                 │                │  5.设备数上限检查（可选淘汰最旧）  │            │
  │                 │                │  6.创建 Session（新 sid，唯一）   │            │
  │                 │                │────────────────────────────────>│            │
  │                 │                │  7.签发 Access + Refresh          │            │
  │                 │                │  8.重置失败计数                   │            │
  │                 │<───────────────│                 │              │            │
  │<────────────────│  200 {accessToken, refreshToken, expiresIn, session}         │
  │                 │                                                  │            │
  │  说明：本次登录只新增一行 Session，其它设备 Session 状态完全不变 → 多点登录成立
```

### 5.2 业务请求鉴权

```
Client ── Authorization: Bearer <accessToken> ──> JwtAuthFilter
   1. 解析并验签 JWT（本地，无 IO）
   2. 校验 exp / iss / aud / typ=access
   3. 校验 pwd_at >= 用户密码修改时间（可从 Redis 或本地缓存）
   4. 查询 auth:revoked:sid:{sid}  → 命中则 401 SESSION_REVOKED
   5. 查询 auth:revoked:user:{id}:after → iat 早于该值则 401
   6. 通过 → 写入 SecurityContext，异步更新 last_active_at（节流：同 sid 60s 一次）
```

### 5.3 令牌刷新（轮换 + 重放检测）

```
Client ── POST /refresh {refreshToken} ──> 服务端
   1. hash = SHA-256(refreshToken)
   2. 按 hash 查 Session
   3. 未找到 → 可能是「已轮换过的旧令牌被重放」：
        a. 若能在 Redis 命中 auth:rt:used:{hash} → 判定重放
        b. 立即撤销该 sid 的整个会话，写审计 REPLAY，返回 401 TOKEN_REPLAY
        c. 触发安全告警（通知用户 + 记录风控事件）
   4. 校验 session.status=ACTIVE 且 refresh_expires_at > now 且 abs_expires_at > now
   5. 生成新的 refreshToken，更新 refresh_token_hash、refresh_expires_at（滑动续期）
   6. 旧 hash 写入 auth:rt:used:{hash}，TTL 5 分钟（窗口内重放可被识别）
   7. 签发新的 Access Token（新 jti，同一 sid）
   8. 返回新令牌对
```

### 5.4 登出与远程踢出

| 场景 | 接口 | 动作 |
| --- | --- | --- |
| 登出当前设备 | `POST /logout` | 撤销当前 sid：更新 DB 状态 → 写 `auth:revoked:sid:{sid}` |
| 登出指定设备 | `DELETE /sessions/{sid}` | 校验 sid 属于当前用户 → 同上传撤销 |
| 登出全部设备 | `POST /logout-all` | 批量更新该用户全部活跃会话 → 写 `auth:revoked:user:{id}:after` |
| 修改密码 | `POST /password/change` | 撤销除当前 sid 外的全部会话，当前会话重新签发令牌 |
| 管理员封禁 | 内部接口 | 撤销全部会话并置 `t_user.status=3` |

### 6.4 错误码

| 错误码 | HTTP | 含义 | 客户端建议动作 |
| --- | --- | --- | --- |
| `OK` | 200 | 成功 | — |
| `AUTH_1001` | 401 | 用户名或密码错误 | 提示，不区分账号是否存在（防枚举） |
| `AUTH_1002` | 423 | 账号已锁定 | 提示剩余锁定时间 |
| `AUTH_1003` | 401 | Access Token 已过期 | 静默调用 `/refresh` |
| `AUTH_1004` | 401 | Access Token 无效 | 清除本地令牌，跳登录 |
| `AUTH_1005` | 401 | Refresh Token 无效或已过期 | 清除本地令牌，跳登录 |
| `AUTH_1006` | 401 | 会话已被撤销 | 提示「已在其它位置登出」 |
| `AUTH_1007` | 429 | 在线设备数超限 | 提示管理设备 |
| `AUTH_1008` | 400 | 验证码错误 | 刷新验证码 |
| `AUTH_1009` | 403 | 账号未激活或已禁用 | 联系管理员 |
| `AUTH_1010` | 401 | 检测到令牌重放，会话已保护性撤销 | 强制重新登录并提示改密 |
| `AUTH_1011` | 400 | 密码强度不足 | 展示规则 |
| `AUTH_1012` | 403 | 无权操作该会话 | 忽略 |
| `RATE_2001` | 429 | 请求过于频繁 | 退避重试 |
| `SYS_5000` | 500 | 系统异常 | 稍后重试 |

### 6.5 客户端接入要点（约定，非服务端实现）

1. **令牌存储**：移动端存 Keychain / Keystore；Web 端 Access Token 放内存变量，Refresh Token 放 `HttpOnly + Secure + SameSite=Strict` Cookie，避免 XSS 窃取。
2. **设备标识**：客户端首次启动生成 UUID 并持久化，作为 `X-Device-Id`，重装应用视为新设备。
3. **并发刷新**：多请求同时 401 时，客户端需用**单飞（single-flight）**机制只发起一次刷新，其余请求挂起等待。
4. **多标签页**：Web 多标签共享刷新结果，避免并发轮换导致重放误判。

## 7. 安全设计

### 7.1 密码与凭证

| 项 | 措施 |
| --- | --- |
| 密码存储 | Argon2id（内存 64MB、迭代 3、并行度 1），或 BCrypt cost ≥ 12；`password_algo` 字段支持渐进升级 |
| 密码强度 | 长度 ≥ 8 且 ≤ 64，禁止常见弱口令字典，禁止与账号/邮箱相同 |
| 传输 | 仅 HTTPS（TLS 1.2+），HSTS；禁止在 URL/日志中出现密码 |
| 凭证泄露防护 | Access Token 短期；Refresh Token 哈希存储 + 轮换 + 重放检测 |
| 签名算法 | RS256 非对称，私钥由 KMS/Secret 管理，支持 `kid` 平滑轮换；**显式拒绝 `alg: none` 与 HS/RS 混淆** |

### 7.2 攻击面防护

| 攻击 | 防护 |
| --- | --- |
| 暴力破解 | 连续 5 次失败锁定 15 分钟；失败计数按账号 + IP 双维度；触发图形验证码 |
| 账号枚举 | 注册/找回接口统一返回文案与耗时；登录失败不区分「账号不存在」与「密码错误」 |
| 撞库 | IP 与设备维度限流；异常地理跳变告警；可接入验证码服务 |
| CSRF | Cookie 模式使用 `SameSite=Strict` + 双提交 Token；纯 Bearer 模式天然免疫 |
| XSS | 响应固定 `Content-Type: application/json`，开启 CSP，不返回 HTML |
| 越权 | 每次会话操作校验 `session.userId == currentUserId`，不做前端信任 |
| 重放（业务请求） | 关键写操作要求 `Idempotency-Key`；JWT 短期有效性限制窗口 |
| 时序攻击 | 密码比较使用恒定时间；不存在的账号也执行一次哑哈希 |
| 日志泄露 | 密码、Token、验证码一律脱敏；手机号/邮箱中间打码 |
| 依赖漏洞 | CI 中执行依赖扫描（OWASP Dependency-Check / Trivy） |

### 7.3 会话策略参数（可配置）

```yaml
auth:
  access-token:
    ttl: 30m                      # Access Token 有效期
    algorithm: RS256
  refresh-token:
    ttl: 30d                      # 滑动有效期
    absolute-ttl: 90d             # 会话绝对上限，到点强制重登
    rotate: true                  # 每次刷新轮换
    reuse-detection: true         # 重放检测
    reuse-window: 5m
    trusted-device-ttl: 180d      # 可信设备延长
  session:
    max-per-user: 5               # 0 = 不限制（多点登录默认限制数）
    max-per-platform: 3
    overflow-policy: EVICT_OLDEST # EVICT_OLDEST / REJECT
    idle-timeout: 30d             # 长期不活跃自动回收
  password:
    min-length: 8
    max-length: 64
    argon2:
      memory: 65536               # KB
      iterations: 3
      parallelism: 1
  lockout:
    max-failed-attempts: 5
    lock-duration: 15m
    captcha-threshold: 3
  revoke:
    blacklist-fallback-ttl: 30m   # Redis 不可用时的本地兜底
```

> 多点登录与上限的关系：默认 `max-per-user: 5` 表示允许最多 5 台设备同时在线（满足「多端并存」），超出时按策略淘汰最久未活跃的会话。若业务要求「无限多端」，将该值设为 0。

### 8.1 日志

- 分级：`INFO` 业务事件、`WARN` 失败与限流、`ERROR` 系统异常。

### 8.2 指标（Prometheus）

### 8.3 告警

| 告警 | 阈值 | 级别 |
| --- | --- | --- |
| 登录失败率突增 | 5 分钟内失败率 > 30% 且样本 > 100 | P1 |
| 令牌重放检测 | 任意 1 次 | P1 |
| 登录 P99 超时 | > 500ms 持续 5 分钟 | P2 |
| Redis 不可用 | 连续 3 次探活失败 | P1 |
| 活跃会话数异常 | 同比波动 > 300% | P2 |

### 8.4 部署形态

**开发/测试**：`docker compose up` 一键拉起 MySQL + Redis + auth-service + Prometheus + Grafana。

**生产**：K8s Deployment 3 副本（无状态），HPA 按 CPU 与 QPS 扩容；MySQL 主从 + 每日全备 + binlog；Redis 哨兵或 Cluster；密钥由 K8s Secret / KMS 注入，禁止写进镜像。

**降级策略**：Redis 故障时，Access Token 校验降级为「仅本地验签 + 短 TTL 容忍」，写操作仍要求数据库校验会话状态；同时熔断登录接口的部分风控逻辑，保证可用性优先。

## 9. 测试策略

| 层级 | 范围 | 工具 | 目标 |
| --- | --- | --- | --- |
| 单元测试 | 领域策略：密码强度、锁定计数、轮换与重放判定 | JUnit 5 + Mockito | 行覆盖 ≥ 80%，核心策略分支 ≥ 95% |
| 集成测试 | 仓储、Redis 黑名单、事务边界 | Testcontainers（真实 MySQL/Redis） | 关键路径 100% 覆盖 |
| 接口测试 | 全部 REST 接口的正反用例 | RestAssured + springdoc 校验 | 契约与文档一致 |
| 安全测试 | 越权、重放、枚举、暴力破解、JWT 篡改 | 自研用例 + OWASP ZAP | 无高危漏洞 |
| 并发测试 | 并发刷新、并发登出、多端同时登录 | JMeter / Gatling | 无死锁、无令牌串号 |
| 压测 | 登录链路与校验链路 | Gatling | 登录 P99 ≤ 200ms；校验 P99 ≤ 20ms |

必测的边界用例清单：

1. 同一账号在两台设备登录 → 两端 Access Token 均可正常访问，互不失效。
2. 设备 A 登出 → 设备 B 仍可访问；A 的 Access Token 立即失效。
3. 同一 Refresh Token 连续使用两次 → 第二次触发重放检测，会话被撤销。
4. 刷新后旧 Access Token 立刻失效（或按策略在 TTL 内仍有效，需明确并测试）。
5. 修改密码 → 其它设备全部失效，当前设备继续可用。
6. 达到设备上限 → 按 `overflow-policy` 正确淘汰或拒绝。
7. 会话绝对过期 → 即使一直在用也强制重登。
8. Redis 宕机 → 服务不整体不可用，降级行为符合预期。
9. 携带 `alg: none` 或被篡改签名的 JWT → 拒绝。
10. 用其它用户的 sid 调用 `DELETE /sessions/{sid}` → 返回 `AUTH_1012`。

**验收标准（DoD）**：全部 P0 用例通过；单元 + 集成覆盖率达标；安全测试无高危；压测达标；OpenAPI 文档与实现一致；README 可按文档一键启动；CI 全绿。

| Tag | `v1.0.0` 语义化版本，Tag 触发发布流水线 |

初始化命令序列：

```bash
# 1. 本地初始化
git init
git branch -M main

# 2. 首次提交前务必确认 .gitignore 生效
git add .
git status          # 检查有没有 application-prod.yml / .env / target/ 被误加
git commit -m "chore: 初始化 auth-service 工程骨架"

# 3. 关联远端并推送
git remote add origin git@github.com:<org>/auth-service.git
git push -u origin main

# 4. 建首个版本标签
git tag -a v0.1.0 -m "chore: 工程骨架与设计文档"
git push origin v0.1.0
```

### 11.2 .gitignore 要点

```gitignore
target/  build/  out/
*.class  *.jar  *.war
.idea/  *.iml  .vscode/  .DS_Store
.env  .env.*  !.env.example
application-local.yml  application-prod.yml
*.log  logs/
*.p12  *.jks  *.pem  *.key
```

**密钥纪律**：任何真实密钥（JWT 私钥、数据库口令、短信 AK/SK）一律不入库。开发用 `.env.example` + 本地 `.env`；生产用 K8s Secret / 云 KMS。若已误提交，必须 `git filter-repo` 清洗历史并轮换密钥。

### 11.3 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>
```

| type | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档 |
| refactor | 重构（不改行为） |
| perf | 性能优化 |
| test | 测试 |
| build / ci | 构建与流水线 |
| chore | 杂项 |

示例：`feat(session): 支持按设备单独撤销会话并写入 Redis 黑名单`

规则：主题 ≤ 50 字符、祈使句、不加句号；正文说明「为什么」；关联 `Refs #123` / `Closes #123`。

### 11.4 CI/CD 流水线

```
push / PR
  ├─ 1. 编译与静态检查    mvn -B verify -DskipTests; Checkstyle; SpotBugs
  ├─ 2. 单元测试          mvn test + JaCoCo 覆盖率门禁（< 80% 失败）
  ├─ 3. 集成测试          Testcontainers 拉真实 MySQL/Redis
  ├─ 4. 安全扫描          OWASP Dependency-Check / Trivy 镜像扫描
  ├─ 5. 契约校验          OpenAPI 与实现比对
  ├─ 6. 构建镜像          多阶段 Dockerfile，打 commit-sha 与语义化标签
  └─ 7. 部署              main 分支 → 测试环境；Tag → 预发 → 生产（人工审批）
```

### 11.5 PR 模板与评审清单

```markdown
## 变更类型
- [ ] feat  - [ ] fix  - [ ] docs  - [ ] refactor

## 变更说明
<!-- 做了什么、为什么 -->

## 验证方式
<!-- 单测/手工/截图 -->

## 自检清单
- [ ] 已补充或更新测试
- [ ] 涉及数据库变更时附 Flyway 脚本且可回滚
- [ ] 无敏感信息、无明文口令与令牌
- [ ] 已更新文档/OpenAPI
- [ ] 破坏性变更已在 CHANGELOG 标注
```

评审重点：安全边界（越权、注入、敏感信息）、事务与并发（会话竞态）、错误码一致性、向后兼容性、可观测性埋点。

### 11.6 发布流程

1. PR 合并到 `main`，CI 全绿。
2. 更新 `CHANGELOG.md` 与版本号（`mvn versions:set`）。
3. `git tag -a v1.x.0 -m "release: v1.x.0" && git push origin v1.x.0`。
4. 流水线自动构建镜像并部署预发 → 冒烟测试 → 人工审批 → 生产。
5. 生产灰度：先 10% 流量，观察 30 分钟核心指标，再全量。
6. 回滚预案：镜像回滚 + 数据库脚本**只做向前兼容**（新增可空列/新表，删除列延后一个版本）。

## 13. 风险与对策

| 编号 | 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- | --- |
| R1 | 多端并发刷新导致误判重放 | 用户被强制登出 | 中 | 客户端单飞刷新；服务端重放窗口设为 5 分钟并记录 IP/UA 辅助判定；Web 多标签共享广播 |
| R2 | Redis 故障导致撤销失效 | 已登出令牌仍可用 | 中 | 缩短 Access Token TTL 至 30 分钟；降级时写本地缓存；Redis 高可用部署 |
| R3 | Refresh Token 泄露 | 账号被接管 | 低 | 轮换 + 重放检测 + 设备列表可见 + 异常登录告警 |
| R4 | 设备上限策略引战 | 用户投诉 | 中 | 默认上限放宽（5 台），淘汰前给用户提示，提供「管理设备」入口 |
| R5 | 时钟偏移导致令牌误判 | 401 抖动 | 低 | 允许 60 秒 skew；容器统一 NTP 同步 |
| R6 | 数据库变更不可回滚 | 发布事故 | 中 | 迁移脚本只做前向兼容；上生产前在预发演练 |
| R7 | 账号枚举与撞库 | 数据泄露风险 | 中 | 统一错误文案、限流、验证码、风控告警 |
| R8 | 隐私合规（IP、手机号） | 合规风险 | 低 | 最小化收集、加密存储、支持导出与删除、保留期策略 |
| R9 | 无状态假设被打破 | 业务服务无法感知撤销 | 中 | 明确业务服务接入规范：校验黑名单或订阅撤销事件 |

## 14. 附录

### 14.1 术语表

| 术语 | 说明 |
| --- | --- |
| 多点登录 | 同一账号在多台设备同时保持登录态，各端会话相互独立 |
| 单点登录（此处语义） | 后登录使先登录失效，仅保留一个活跃会话（本项目**不采用**） |
| Access Token | 短期访问令牌，JWT 格式，用于业务接口鉴权 |
| Refresh Token | 长期刷新令牌，不透明随机串，仅用于换取新 Access Token |
| 会话（Session） | 一次登录产生的服务端记录，标识一台设备的一条登录态 |
| 令牌轮换 | 每次刷新都签发新的 Refresh Token 并使旧的失效 |
| 重放检测 | 已失效的 Refresh Token 再次被使用时判定为泄露并撤销会话 |
| 黑名单 | Redis 中记录已撤销会话，用于让 Access Token 提前失效 |

### 14.2 参考规范

- RFC 6749 / 6750 —— OAuth 2.0 授权框架与 Bearer Token 用法
- RFC 7519 —— JSON Web Token
- RFC 9700 —— OAuth 2.0 安全最佳实践（BCP）
- RFC 8725 —— JWT 最佳实践
- OWASP ASVS 4.0（V2 认证、V3 会话管理）、OWASP Top 10
- NIST SP 800-63B —— 数字身份认证指南（密码与限流建议）
